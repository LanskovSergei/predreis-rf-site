# Пояснения к демо-калькулятору

## Почему отдельный репозиторий

По твоему решению — не трогаем текущий `App.tsx` в EPL_Calculator (там уже
готовый Шаг 1.2: брендинг, поле адреса АЗС/стоянки, маршрут с картой,
редактирование с пересчётом — твоя собственная работа). Демо — независимый
проект, который просто ходит в тот же бэкенд.

## Дизайн-концепция

Референсы (calcus.ru, kalkulaator.ee) — простые одностраничные
маркетинговые калькуляторы «расход/стоимость поездки», очень чистый UX. Это
другая, более простая задача, чем наш калькулятор — взял только уровень
простоты и полировки, содержание осталось наше (восстановление ПЛ).

**Концепция**: путевой лист как физический документ. Форма подана как
отрывной бланк с перфорацией между разделами, номером и «датой выдачи»
как на настоящем ПЛ. Показания (одометр, литры, время) — моноширинным
шрифтом (IBM Plex Mono), как на приборной панели. Заголовки — Manrope
(800). Палитра: тёмно-синий «асфальт» + холодная бумага бланка + янтарный
акцент (дорожная разметка) + тёмно-бирюзовый (маршрут/данные) + красный
«штамп» для предупреждений.

## Что упрощено относительно основного (внутреннего) инструмента

- Один водитель вместо календаря на нескольких — рабочие дни задаются
  кружками Пн–Вс + кнопкой «Все будние дни» (даты генерируются на лету
  при отправке через `ВходныеДанные.водители[0].дни`).
- «Дополнительные параметры» (средний расход, одометр на старте, вид
  сообщения, коэффициенты) свёрнуты по умолчанию.
- Результат — карточки-«корешки» путевых листов с ключевыми цифрами, без
  второстепенных деталей.

## Откуда брать calc.ts / types.ts при обновлении

Эти файлы — копии из основного репозитория
(`EPL_Calculator/src/calc.ts`, `EPL_Calculator/src/types.ts`) на момент
создания демо (после коммита `558de66`, где ты добавил маршрут/адреса в
`calc.ts`). Если в основном проекте логика расчёта поменяется — обнови эти
два файла здесь вручную (простое копирование, импорты внутри файлов не
трогать — они самодостаточны).

## api.ts: кросс-доменный вызов и тестируемость

В отличие от `api.ts` в основном проекте (там относительный путь `/api/...`,
подхватываемый nginx/dev-прокси), здесь вызов всегда абсолютный —
`VITE_API_URL` обязателен для реального расчёта (без него — сразу офлайн-режим).

Технический нюанс: `VITE_API_URL` читается через `(import.meta as any).env`,
и Vite **статически заменяет** `import.meta.env.VITE_*` при трансформации
файла — поэтому `vi.stubEnv()` в тестах не может подменить значение
постфактум (транспиляция уже произошла). Решение — явная тестовая точка
подмены `__setApiBaseForTests()` в `api.ts`, используется в `api.test.ts`.
Если понадобится добавить похожие env-зависимые тесты — используй тот же
паттерн, а не `vi.stubEnv`.

## Проверено

- `npm test` — 11/11 тестов зелёные (включая новые: ошибка при отсутствии
  `VITE_API_URL`, откат на офлайн-движок без него).
- `npm run build` — собирается чисто (TS + Vite).
- Живой прогон: реальный бэкенд из EPL_Calculator отвечает корректно;
  подтвердил, что CORS **режет** запрос с origin, которого нет в
  `ALLOWED_ORIGINS` бэкенда — то есть на проде обязательно добавить домен
  демо в `ALLOWED_ORIGINS` (см. `deploy/DEPLOY.md`, Шаг 0).
- Визуально (скриншот) — не проверял, в песочнице нет браузера. Глянь
  глазами через `npm run dev` или после деплоя.
